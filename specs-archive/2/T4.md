# Lane T4 — Typed preview client

## What landed

`preview(lines): Promise<DocumentResult>` in `apps/frontend/src/lib/api/pricing.ts`:

- POSTs `{ lines }` to `/api/v1/pricing/preview` through the existing `apiFetch` (credentials,
  envelope handling, `ApiError` all inherited — `client.ts` untouched).
- Debounces at `PREVIEW_DEBOUNCE_MS = 300` (exported for T5): calls within the window coalesce;
  one request fires, carrying the last call's lines; every caller in the window resolves with
  that response.
- Stale-response guard (R9): each fired request takes a monotonic sequence number; a settling
  response whose sequence is no longer the latest is dropped — neither resolved nor rejected —
  so an older reply landing last never overwrites a newer total.
- Errors: `ApiError` propagates to all waiters of the latest request unchanged
  (code/message/details); a stale request's rejection is dropped along with its result.

## Assumptions

- Debounce window of 300 ms — the ARCH names no value; exported as `PREVIEW_DEBOUNCE_MS` so T5
  (or a later amendment) has one place to change it.
- Dropped (stale) calls leave their promises pending forever by design: "the caller only ever
  observes the newer result". The superseding newer call always settles, which is what T5's
  pending state needs. Sequence invalidation happens at request-fire time, not call time, so a
  debounce-pending edit does not strand an already-issued request's response.
- No arithmetic anywhere in the client: it only serializes inputs and hands back
  `DocumentResult` as received.

## For the join / T5

- T5 should consume `preview()` and may import `PREVIEW_DEBOUNCE_MS`; a `.then` handler on the
  latest call is sufficient for pending-state handling — dropped calls settle never, latest
  settles always.
- Line identity is positional (A7): this client sends only the 4 calculation fields per line.
