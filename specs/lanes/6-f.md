# Lane 6-F — CI/CD pipeline

## Status

`6-F1` (CI half) — **done**. `6-F2` (CD half) — **implemented; awaiting first production deployment after the human configures repository secrets and branch protection**.

## What landed

- `.github/workflows/ci.yml` — an unfiltered `ci` workflow, so both required checks complete on every pull request. Its `backend-ci` and `frontend-ci` jobs run `npm ci` → typecheck → test → production Docker build, then upload `backend-image` and `frontend-image` artifacts for one day.
- The frontend build passes `BACKEND_ORIGIN=http://backend:3001`; Next consumes this during `next build`, allowing its same-origin proxy to reach the backend over the Compose `internal` network.
- One `deploy` job needs both CI jobs, downloads both artifacts from that same run, and is limited to `main` pushes or an explicit dispatch of `main`. Its production concurrency group cancels superseded deploys, so a shared Compose stack cannot start without both images or roll back to an older overlapping run.
- The deploy job rsyncs `infra/` without `--delete`, preserving droplet-only `infra/.env`; it loads both images, runs Compose without rebuilding, and retries both the public health endpoint and site root.
- All GitHub Actions are pinned to reviewed commit SHAs. The SSH host key comes from `DEPLOY_KNOWN_HOSTS`, an independently verified repository secret, rather than live `ssh-keyscan` output.

## Verification

- Local CI-equivalent verification on 2026-08-13: backend `npm run typecheck`, `npm test` (193 passed, 111 skipped), and Linux/amd64 Docker build passed; frontend `npm run typecheck`, `npm test` (85 passed), `npm run build`, and Linux/amd64 Docker build with the internal backend origin passed.
- The built frontend image contains `/api/*` and `/auth/*` rewrites targeting `http://backend:3001`.
- The production Compose file and Caddyfile validate locally. After this workflow revision is pushed, GitHub Actions must complete both required CI jobs before merge.

## For the human

1. Add `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, and the independently verified `DEPLOY_KNOWN_HOSTS` repository secrets exactly as described in `specs/lanes/deployment.md`.
2. In **Settings → Branches**, require the `backend-ci` and `frontend-ci` checks from the unfiltered `ci` workflow. Do not require path-filtered workflows; none remain.
3. Set the production `JWT_SECRET` in `~/multiprice/infra/.env` before the first deploy, then trigger a `main` deployment and perform the browser smoke test.

## Assumptions

- CI runs both app jobs for every PR. This deliberately trades path-filter build avoidance for branch-protection checks that always reach a terminal state.
- Each app image is built once per workflow run and passed to the single deploy job as an artifact; CD never rebuilds it.
- MongoDB and Caddy are pinned to reviewed multi-architecture image-index digests. Update a digest only through a deliberate image review.
- Docker build step duplicates work the app's own multi-stage Dockerfile already does (typecheck happens twice: once bare, once inside the Docker build). Left as-is — matches `../multip`'s CI, and the bare run fails faster/cheaper before paying for a Docker build.
