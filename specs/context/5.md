
The scored claim is that finalized documents are immutable **via the API**. 4-B is a separate lane because that claim deserves evidence written independently of the guard that implements it.

`G4` runs in wave 6 (beside `G5`); `4-A`, `4-B` and `4-C` run in wave 7. `4-D` starts only after J4 is green, in wave 8. It is stretch goal 1, and the plan places it here — while the create and finalize paths are loaded context — rather than in Phase 6.

## Gate G4 — Lifecycle contract

**Agent** backend-engineer · **Depends on** J3 · **Blocks** 4-A, 4-B, 4-C

**Mission** Fix the finalize response, the rejection code, and the route registry that both the guard and its test read from.

**Owns** `apps/backend/src/contracts/lifecycle.ts` (schemas **and** this domain's error codes), `apps/backend/src/api/routes/registry.ts`, `apps/frontend/src/lib/api/types/lifecycle.ts`, `docs/contracts/phase-4.md`

**Build**
1. `POST /api/v1/documents/:id/finalize` returns the finalized document — same shape as a GET, `status: 'finalized'`. No new response type; a distinct one invites the UI to drift.
2. The rejection: **409** with code **`DOCUMENT_FINALIZED`**. The plan's Phase 4 prose writes it lowercase; that contradicts the project-wide `SCREAMING_SNAKE` convention every other code follows, and a single odd-cased literal that the frontend and three test files match on is a bug waiting to happen. It is corrected here, deliberately. Message names the document and says finalization is irreversible.
3. **The guarded-route registry** — `api/routes/registry.ts` exports the routes that mutate an **existing** document. Note what is absent: `POST /api/v1/documents` creates one, and guarding it would reject every new document by looking up a status that does not exist yet. "Mutating" in G3's table and "guarded" here are not the same set, and the difference is exactly one route:
   ```ts
   export const GUARDED_ROUTES = [
     { method: 'PATCH',  path: '/api/v1/documents/:id' },
     { method: 'DELETE', path: '/api/v1/documents/:id' },
     { method: 'POST',   path: '/api/v1/documents/:id/lines' },
     { method: 'PATCH',  path: '/api/v1/documents/:id/lines/:lineId' },
     { method: 'DELETE', path: '/api/v1/documents/:id/lines/:lineId' },
     { method: 'POST',   path: '/api/v1/documents/:id/finalize' },
   ] as const
   ```
   4-A's guard is applied from this list; 4-B's test iterates the same list. A route added later without an entry is then a deliberate omission, not an oversight — and the plan's requirement that "adding a route that escapes it requires deliberately editing this list" is structurally true rather than a hope.
4. Finalize preconditions: the document is a draft (finalizing twice is 409 `DOCUMENT_FINALIZED`), it has at least one line — rejected with **`DOCUMENT_HAS_NO_LINES`**, a code added here because no existing code means it and "pick the closest one" produces a wrong message on a scored requirement — and its persisted lines still pass the normal document validator. That last one is stretch goal 2 — the PDF asks for finalize validation rejecting invalid quantities or negative prices, and reusing the ordinary validator covers it without a second validation subsystem.
5. Duplicate contract, declared now and implemented only if 4-D runs: `POST /api/v1/documents/:id/duplicate` → **201** with a new **draft**, fresh document and line ids, recomputed totals, title suffixed `(copy)`, `issueDate` set to today. A finalized document may be duplicated — that is the point of the stretch goal.
6. Mirror the finalize and duplicate response types and the 409 code into `apps/frontend/src/lib/api/types/lifecycle.ts`. Write `docs/contracts/phase-4.md`, including the registry table.

**Done when** both apps typecheck and the registry exports every existing-document mutation from G3's table — six routes, excluding `POST /documents`.

**Guardrails** No guard implementation, no route bodies.

## Lane 4-A — Finalize and the immutability guard

**Agent** backend-engineer · **Depends on** G4 · **Parallel with** 4-B, 4-C

**Mission** One finalize route, and one guard that no mutating route can be registered without.

**Owns** `apps/backend/src/api/routes/documents-lifecycle.ts`, `apps/backend/src/api/plugins/immutability.ts`, `apps/backend/src/services/lifecycle.ts`, colocated `*.test.ts`

**Reads, never edits** `src/contracts/lifecycle.ts`, `src/api/routes/registry.ts`, `src/services/documents.ts`, `src/pricing/**`

**Build**
1. **The guard is a global hook, not a per-route annotation** — necessarily, because the routes it protects live in 3-A's files and you may not edit them. It goes in `src/api/plugins/immutability.ts`, **wrapped in `fastify-plugin`**, where G0's plugin autoloader picks it up before routes are registered.

   Both halves of that matter. Dropping the file in without `fp` gives you an encapsulated plugin whose `preHandler` applies to itself and protects none of Phase 3's sibling routes — and it would pass a test that exercises the plugin directly. Registering it from inside your own lifecycle route file has the same failure. `fp` + plugin autoload is the only combination that reaches routes another lane wrote.

   The hook loads the target document (owner-scoped, so a foreign id is still 404 and never 409 — a 409 on someone else's document reveals that it exists) and rejects with 409 `DOCUMENT_FINALIZED` when its status is `finalized`. It runs after `authenticate` and before the handler.
2. Apply the guard from `GUARDED_ROUTES`, not by hand-annotating each route. Prefer wiring it so a mutating route that is missing from the registry is detectable at boot — a startup check comparing Fastify's registered routes against the registry, failing loudly on a mismatch, is cheap and turns the plan's "deliberately editing this list" into an enforced invariant.
3. `POST /documents/:id/finalize` — guard applies (finalizing a finalized document is 409), then: recompute totals from the persisted lines with the Phase 1 engine, run the **normal document validator** over them, and reject invalid persisted data with the ordinary specific codes. Only then flip status. Defensive reuse, not a parallel validation path.
4. Empty document: finalizing a document with no lines is rejected. Pick the code from the existing enum rather than inventing one, and record the choice in your report.
5. The finalize write is a single conditional update — `{ _id, ownerId, status: 'draft' }` → `{ status: 'finalized' }`. If it matches nothing, someone finalized concurrently: return 409, do not re-read and retry. Embedded lines mean this is one atomic document write with no transaction.
6. After finalize, the stored totals are the ones computed at finalize time. Note in your report whether they changed; if they did, the draft was persisted with stale totals and that is a 3-A bug worth surfacing at the join.

**Done when** `cd apps/backend && npx vitest run src/api/plugins src/services/lifecycle*` is green and the boot check reports every mutating route guarded.

**Guardrails** Do not write into `test/api/**` — 4-B owns the immutability suite. No duplicate endpoint; that is 4-D, after J4.

## Lane 4-B — Immutability evidence

**Agent** test-engineer · **Depends on** G4 · **Parallel with** 4-A, 4-C

**Mission** One parameterized test enumerating every mutating route against a finalized document. This file is the evidence for a scored row; treat it as a deliverable, not as coverage.

**Owns** `apps/backend/test/api/immutability.test.ts`, `apps/backend/test/api/finalize.test.ts`

**Reads, never edits** `docs/contracts/phase-4.md`, `src/api/routes/registry.ts`, `test/support/factories.ts`

**Build**
1. Import `GUARDED_ROUTES` from the registry and iterate it. **Do not hand-list the routes** — the whole design of G4 is that this test and the guard read the same source, so that a route added without an entry fails visibly in one place rather than silently passing in two.
2. For each mutating route against a finalized document: **409**, code `DOCUMENT_FINALIZED`, and — the part usually missed — assert that **the document is unchanged afterwards**. A route returning 409 while having already written is still a lifecycle failure, and only a re-read catches it.
3. Each route with a valid body and with an invalid one: both 409. The lifecycle check precedes validation, so a finalized document never reports a field error instead of its status.
4. Non-guarded routes against a finalized document still behave normally — `GET /documents/:id` returns 200, and **`POST /documents` still creates a document** while a finalized one exists. A guard applied too broadly is the other failure mode, and creation is where it would land.
5. `finalize.test.ts`: finalize a valid draft → 200, status flips, totals match the fixture's `421.50`; finalize twice → 409; finalize a document whose persisted lines are invalid → rejected with the specific field code, not a generic 409; finalize an empty document → rejected; finalize another user's document → 404.
6. Add a test asserting the registry covers every existing-document mutation Fastify has registered, if 4-A exposed the boot check. If it did not, hand-verify against `docs/contracts/phase-3.md` and note the gap in your report.

**Done when** the suite runs and every assertion is meaningful (no `expect(true)` placeholders). Red where 4-A has not landed yet is expected; report the split.

**Guardrails** Test files only. Do not adjust the registry to make a test pass — that is an amendment.

## Lane 4-C — Locked document UI

**Agent** frontend-engineer · **Depends on** G4 · **Parallel with** 4-A, 4-B

**Mission** Finalize as a deliberate act, a read-only view that looks intentional, and a 409 from a stale tab that says what happened.

**Owns** `apps/frontend/src/components/lifecycle/**` (finalize dialog, status banner), `apps/frontend/src/app/(app)/documents/[id]/view/page.tsx`, `apps/frontend/src/app/(app)/documents/[id]/page.tsx` *(3-D's editor page — transferred to you for this wave; 3-D landed in wave 5 and is not running)*, `apps/frontend/src/components/document-editor/**` *(same transfer)*, `apps/frontend/src/lib/api/lifecycle.ts`, colocated `*.test.tsx`

**Ownership note** You cannot deliver this lane without editing the editor page and its save path: routing a finalized document to the read-only view happens there, and so does handling a 409 on save. Ownership is a lock for the wave, not a permanent assignment — see `docs/parallel-execution.md` § Ownership is per-wave.

**Reads, never edits** `src/lib/api/documents.ts`, `src/lib/api/types/lifecycle.ts`, `design/htmls/document-view.html`, `design/htmls/document-edit.html`

**Build**
1. `lib/api/lifecycle.ts` — `finalize(id)`, and `duplicate(id)` declared but unused until 4-D.
2. Finalize confirmation dialog: irreversible, says so in those terms, names the document, keyboard-accessible, focus-trapped, cancel is the default action.
3. Read-only view from `design/htmls/document-view.html` — the finalized document rendered as a record rather than as a disabled form. Disabled inputs everywhere is the lazy version and it looks like a bug.
4. Routing: a finalized document opens in the read-only view; a draft opens in 3-D's editor. Handle the transition after a successful finalize without a full reload.
5. **The stale-editor case.** An editor open on a draft that was finalized elsewhere receives 409 `DOCUMENT_FINALIZED` on save. Surface it as a clear, non-destructive message — the document has been finalized, here is the current state — and switch the view to read-only. Never silently discard the user's unsaved edits without telling them, and never leave a spinner running.
6. Component tests where the behavior is real: the confirm dialog calls finalize only on confirm, and the 409 handler transitions to the locked state with a visible message.

**Done when** `cd apps/frontend && npm test && npm run build` exits zero.

**Guardrails** Do not enforce immutability in the browser as the mechanism — the API is the enforcement point and the scored claim. The UI reflects the state; it does not defend it. No duplicate button until 4-D.

## Lane 4-D — Duplicate (stretch goal 1)

**Agent** backend-engineer, then frontend-engineer · **Depends on J4 being green** · Runs in wave 8

Skip this lane entirely if anything above is red. The required flow outranks every stretch goal.

**Owns** `apps/backend/src/api/routes/documents-duplicate.ts`, `apps/backend/test/api/duplicate.test.ts`, `apps/frontend/src/components/documents/duplicate-action.tsx`, plus — transferred for this wave, since 3-C and 4-C have both landed — `apps/frontend/src/components/documents/**` and `apps/frontend/src/app/(app)/documents/[id]/view/page.tsx`, which is where the action has to be wired in

**Build**
1. `POST /documents/:id/duplicate` per G4's contract — new draft, fresh document and line ids, totals recomputed by the engine rather than copied, title suffixed `(copy)`, `issueDate` today, owner is the requester. A finalized source is explicitly allowed; that is the goal's purpose.
2. Duplicating another user's document is 404.
3. The source document is untouched. Assert it — this is the one route that reads a finalized document and writes, and the immutability claim covers it.
4. Frontend: a duplicate action on the list row and in the read-only view, navigating to the new draft on success.
5. Note the feature in `specs/lanes/4-D.md` for 6-A, which writes the README's stretch-goals section in wave 9.

**Done when** `npx vitest run test/api/duplicate.test.ts` is green and the action works end to end.

**Guardrails** Do not add duplicate to `GUARDED_ROUTES` — it creates a new document rather than mutating the source, and guarding it would break duplicating a finalized document, which is the entire feature.
