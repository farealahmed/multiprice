# Phase 5 — Summary report (lane briefs)

Plan context: `docs/implementation-phases.md` § Phase 5. Rules: `docs/parallel-execution.md`.

```
G5 ──► ┌─ 5-A aggregation + reconciliation ─┐
       └─ 5-B report UI ────────────────────┴─► J5
```

`G5` runs in wave 6 beside `G4`; `5-B` then runs in wave 7 alongside Phase 4's lanes — the report page builds against the contract and needs nothing from the lifecycle work. `5-A` follows in wave 8.

## Gate G5 — Report contract

**Agent** backend-engineer · **Depends on** J3 · **Blocks** 5-A, 5-B

**Mission** Fix the range query, the summary shape, and the date semantics that decide which documents count.

**Owns** `apps/backend/src/contracts/report.ts` (schemas **and** this domain's error codes), `apps/backend/src/contracts/document.ts` *(one amendment only — the list query, see step 2)*, `apps/frontend/src/lib/api/types/report.ts`, `apps/frontend/src/lib/api/documents.ts` *(transferred from G3 for this wave)*, `docs/contracts/phase-5.md`

**Build**
1. `GET /api/v1/reports/summary?from=YYYY-MM-DD&to=YYYY-MM-DD` →
   ```ts
   ReportSummary {
     from: string; to: string
     documentCount: number
     totalGrandTotal: number   // major units
     totalTax: number
     totalDiscount: number
   }
   ```
   Exactly the four figures the PDF asks for: number of documents, sum of grand totals, sum of total tax, sum of total discount.
2. **Amend the document list to accept the same range** — `GET /api/v1/documents?from=YYYY-MM-DD&to=YYYY-MM-DD`, both optional, same inclusivity and same date semantics as the report. Add the query schema to `contracts/document.ts` and the parameters to `lib/api/documents.ts`.

   This is a gap, not an embellishment: 5-B renders the in-range document table beneath the summary cards, and J5 reconciles the cards against those rows — but G3 froze the list route with no date filter, so as written there is no API that can return them. Fetching every document and filtering in the browser is not an option; it would make the screen's own claim unverifiable at any realistic size, and the reconciliation would be testing the frontend's filter rather than the aggregation.

   Keeping the filter on `/documents` rather than returning rows inside `ReportSummary` keeps the summary a summary, and gives 5-B one obvious call per thing it displays.

3. **Both ends inclusive.** A document issued on `from` counts; a document issued on `to` counts. Say so here, test it in 5-A, state it in the UI, and repeat it in the README — off-by-one at a range boundary is the single most likely correctness bug in this phase.
4. **The timezone rule, written down once:** `issueDate` is a calendar date stored as `YYYY-MM-DD` (G3's decision). The comparison is a plain string range on that field. No `Date` object, no UTC conversion, no server locale involved — a document issued on the 1st is in that month for every viewer on earth. Write the sentence here; the README quotes it.
5. **Scope: all documents in range, drafts included.** The plan's decision, and it needs stating in three places — the contract, the UI, and the README. The PDF filters the report by issue date and says nothing about status; filtering by status would be an unstated narrowing of the requirement. This is an assumption, and it is documented as one.
6. Codes, exported from `contracts/report.ts` itself: `DATE_RANGE_INVALID` (unparseable or not `YYYY-MM-DD`), `DATE_RANGE_INVERTED` (`from > to`). Both are 400 with the offending parameter's path.
7. Mirror `ReportSummary` and the codes into `apps/frontend/src/lib/api/types/report.ts`; write `docs/contracts/phase-5.md` with the endpoint, the inclusivity rule, the timezone sentence, and the draft-inclusion assumption.

**Done when** both apps typecheck and `docs/contracts/phase-5.md` carries all three policy statements verbatim.

**Guardrails** No aggregation, no page.

## Lane 5-A — Report aggregation

**Agent** backend-engineer · **Depends on** G5, J3 · **Parallel with** 5-B

**Mission** One owner-scoped aggregation whose output provably equals the sum of the documents a user can see in the range.

**Owns** `apps/backend/src/api/routes/reports.ts`, `apps/backend/src/services/reports.ts`, `apps/backend/src/persistence/reports.repository.ts`, `apps/backend/src/api/routes/documents.ts` *(one change only — the date-range filter on the list route; transferred from 3-A for this wave)*, `apps/backend/src/persistence/documents.repository.ts` *(same)*, `apps/backend/test/integration/reports.test.ts`, colocated `*.test.ts`

**Reads, never edits** `src/contracts/report.ts`, `src/persistence/repository.ts`, `test/support/factories.ts`, `test/fixtures/pdf-sample.ts`

**Build**
1. The route file goes in `src/api/routes/` and autoloads itself — never edit `app.ts`. One Mongo aggregation: `$match` on `{ ownerId, issueDate: { $gte: from, $lte: to } }`, then `$group` summing the persisted `totals` fields and counting documents. `ownerId` is inside `$match` — never a post-filter, per G2's rule. Do not fetch documents and sum in Node; the aggregation is the implementation and the reconciliation test is what proves it right.
2. Sum the **persisted** totals that Phase 3 recomputed on write. Do not re-run the engine per document here — if stored totals were wrong, the report agreeing with a fresh computation would hide it, and the reconciliation test would pass while the documents on screen disagreed.
3. Empty range returns zeros and `documentCount: 0`, not 404. A report with no documents is a valid answer.
4. Money: the aggregation sums integer cents; convert to major units once, at the service boundary. Summing rounded major-unit floats across many documents is exactly the drift the PDF warns about.
5. Validate `from`/`to` with G5's schema; `from > to` is 400 `DATE_RANGE_INVERTED`. Attach the `authenticate` preHandler.
6. Implement G5's list-route amendment: `GET /documents?from=&to=` filters on `issueDate` with the same inclusive bounds and the same owner scoping. One shared date-filter helper between the list query and the aggregation `$match` — if the two ever disagree about a boundary, the report and the table beneath it disagree on screen, which is precisely the scored failure.

**Tests — the reconciliation test is the deliverable**
1. **Reconciliation, verbatim from the criterion**: seed N documents across a range, list them through `GET /documents?from=&to=` with the same range, sum their grand totals, tax, and discount in the test, and assert the report's figures are exactly equal. Using the same range on both calls is the point — it tests the two code paths against each other, which is what J5 then repeats on screen. Not approximately — exactly, in cents. Use varied lines including the PDF sample so the numbers are non-trivial.
2. Boundaries: documents issued exactly on `from` and exactly on `to` are included; the day before `from` and the day after `to` are excluded.
3. Isolation: another user's documents in the same range never contribute to the count or any sum. Seed a second user with larger totals so a leak is unmistakable.
4. Drafts are included, and a mixed draft/finalized range reconciles — the assumption, tested.
5. A single document appearing in two overlapping ranges contributes fully to each.
6. Empty range returns zeros.

**Done when** `cd apps/backend && npx vitest run test/integration/reports.test.ts` is green.

**Guardrails** No new totals arithmetic — sums of stored figures only. No status filter.

## Lane 5-B — Report page

**Agent** frontend-engineer · **Depends on** G5, J3 · **Parallel with** 5-A and all of Phase 4

**Mission** The report screen from the mockup, where the cards and the table below them visibly agree.

**Owns** `apps/frontend/src/app/(app)/report/**`, `apps/frontend/src/components/report/**` (range picker, stat cards, in-range table), `apps/frontend/src/lib/api/reports.ts`, colocated `*.test.tsx`

**Reads, never edits** `src/lib/api/types/report.ts`, `lib/api/documents.ts`, `design/htmls/report.html`, `src/styles/tokens.css`

**Build**
1. `lib/api/reports.ts` — typed `summary(from, to)` through the shared client.
2. Range inputs with sensible defaults (current month) from `design/htmls/report.html`. `from > to` is caught before the request and shown inline; do not make the server say it, though it also will.
3. Four stat cards: document count, sum of grand totals, sum of tax, sum of discount. Tabular numerals, the mockup's card treatment, 2 decimal places.
4. The in-range document table beneath the cards, from `documents.list({ from, to })` — the range parameters G5 added for exactly this. **This adjacency is the point of the screen** — the criterion is that the summary matches the individual documents, and a reviewer should be able to check it by eye without opening devtools.
5. **State on screen that both draft and finalized documents are included**, and that both range ends are inclusive. Not in a tooltip — visible text near the range inputs. This is where the assumption from G5 becomes something a reviewer can see rather than something buried in the README.
6. Empty state: "no documents issued between X and Y", with the range echoed back.
7. Loading and error states; a failed request offers a retry.
8. A component test for the `from > to` inline validation, if that logic lives in the component rather than in a shared validator.

**Done when** `cd apps/frontend && npm test && npm run build` exits zero.

**Guardrails** No summing in the browser — the cards render server figures, the table renders server documents. If they disagree, that is a backend bug the screen is designed to reveal, not something the frontend reconciles.
